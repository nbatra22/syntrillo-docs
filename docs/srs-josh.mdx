## Event Triggers

1. Onboarding Form Submission (Healthie webhook - form)
2. Risk Factor Group Update
   1. Medical History (Internal - form submission)
   2. Lab Values (Healthie webhook - metric entry)
   3. Substance Use (Internal - form submission)
   4. Blood Pressure (Internal - BP analysis lambda \*\*\* every 1 month instead of 2)
   5. Tests/Orders (TBD - Healthie webhook or Internal)
   6. Physical Activity (Healthie webhook - form)

All Healthie webhook events would be sent to our (not yet created) Lambda function endpoint, which would read the payload then, depending on event type, query the corresponding event data (either form answers or metric entries) from Healthie and save the data to their respective datatables as needed.

More information on each grouping is below.

### Blood Pressure

Our most abundant pool of data. Best case scenario is that each patient records at least one measurement a day since baseline. These values can be grabbed directly from tenovi_raw_measurements. Note 'value_1' is systolic and 'value_2' is diastolic. Also make sure to query by 'blood_pressure' for 'metric_name', but you should probably just use the BloodPressureAnalysis class too.

The only BP metrics we care about for the SRS calculation is the following:

- Average SBP
- Average DBP
- SBP Variability (std. deviation)
- SBP Peak (avg. of 3 highest measurements)

The only caveat here is that we need to handle the timeframes differently depending how far along the patient has been under our care. The basic rule of thumb is to check if the patient's first measurement is less than or greater than 4 weeks time. If the former is true, use Baseline values (first two weeks). If the latter is true, use 1 month trailing values.

The link above includes all of the metrics we'd want to show somewhere in the display. Here's the updated list of columns:

- **metric_key**: this will serve as a unique metric identifier which should be used across relative tables like medical_history and substance_use
- **display_name**: long metric naming convention to be used in frontend
- **short_name**: shortened metric naming convention to be used in frontend
- **unit** (optional)
- **calc_type**: depdenist vs. independent risk factor
- **compliance**: boolean value to determine whether we need to track treatment compliance / optimization
- **dependency**: list of related fields that are required for specified metric to be not null
- **factor_group**: risk factor metric group / bucket / type
